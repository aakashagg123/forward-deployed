AI-assisted development — recap & real-world examples

Real-world examples

A controlled trial: faster on a defined task (2023). Peng and colleagues gave developers a task, with and without an AI pair programmer, and measured completion time. The group with the assistant finished faster. 🎯 Takeaway: on a well-defined task with a clear check, the gain is real. Do not assume it carries to all work.

An RCT with the opposite result (2025). METR ran a randomized trial with experienced open-source developers working on their own repositories. They were slower with the AI tools, though they had expected to be faster. 🎯 Takeaway: perception is not measurement. Context, codebase familiarity and review cost change the answer.

Anthropic's own guidance: give the agent a way to check. The Claude Code best-practice pages say the single most useful thing is to give the agent a way to verify its work, such as tests or a script. 🎯 Takeaway: verification is the product. Name the check in every spec.

Documented limits of command rules. The Claude Code permissions page states that a Bash rule matches the command as written and lists forms it does not catch. 🎯 Takeaway: rules are guardrails, not walls. Use a sandbox for unattended work.

A published cost anchor. The Claude Code cost page reports about $13 per developer per active day on average across enterprise deployments, and under $30 for 90% of users. 🎯 Takeaway: cost is per task and per session, and a pilot gives your own number.

The through-line. A coding agent moves the work from writing to deciding and checking. Leaders who get value write precise specs, make "done" a fact, limit what the agent can touch, plan for the review queue, and measure outcomes without being fooled by averages.

Walk-away question: "For our agent rollout: can I name the check that proves a change works, what the agent cannot touch, the cost of a batch and its review hours, and the outcome metric split by difficulty?"

Test yourself

  1. An agent cuts run time to zero. Why does a task not get ten times faster?

    AnswerSpecifying and reviewing remain, and rejected attempts repeat them. In the model, an instant agent with weak checks reached only 2.19 times the speed of working by hand. (Lesson 1)

  2. Which helps more in the model: a faster agent or stronger checks?

    AnswerStronger checks. Strong checks took the task from 146 to 84 minutes. An instant agent with weak checks only reached 132. (Lesson 1)

  3. What four parts does a good task spec have?

    AnswerThe goal, the scope, the constraint that matters, and a way to check the result. (Lesson 2)

  4. Why does splitting a long context file into imports not cut its cost?

    AnswerImported files load at launch with the main file. To cut cost, move content into path-scoped rules or skills, which load only when relevant. (Lesson 2)

  5. What should and should not go in a context file?

    AnswerInclude commands and rules the agent cannot infer from the code. Leave out descriptions of the code, vague advice, duplicates and long explanations. (Lesson 2)

  6. Why is an agent's "all tests pass" not evidence?

    AnswerIt is a sentence, and the agent may not have run the tests or may have weakened them. A command that exits with pass or fail is evidence. (Lesson 3)

  7. How does a Stop hook enforce a check, and what prevents an endless loop?

    AnswerIt runs the check when the agent tries to stop and exits 2 with a message if it fails, which keeps the agent working. A guard on `stop_hook_active` and a cap on consecutive blocks end the loop. (Lesson 3)

  8. In what order are permission rules evaluated?

    AnswerDeny, then ask, then allow. The first match wins, so a broad deny beats a narrow allow. (Lesson 4)

  9. A rule denies curl. Does that stop /usr/bin/curl or sh -c 'curl …'?

    AnswerNo. A Bash rule matches the command as written. Use a sandbox when you need a real boundary. (Lesson 4)

  10. When is bypass mode acceptable?

    AnswerOnly in an isolated environment, such as a container with no secrets and a limited network. (Lesson 4)

  11. Five unrelated tasks run in one long session cost $14.88 of input. In five fresh sessions they cost $5.28. Why?
    AnswerEvery turn re-reads the whole history. A long session carries earlier tasks along. Clear the context between unrelated tasks. (Lesson 5)
  12. Three attempts instead of one raised cost from $300 to $417 for 200 tasks. What else changed?
    AnswerAccepted tasks rose from 140 to 195 and hand-offs fell from 60 to 5. Review hours also rose from 14 to 19, so the review team is the limit. (Lesson 5)
  13. A dashboard shows cycle time down from 23 to 7.1 hours. What do you check before celebrating?
    AnswerThe mix of work. Split by difficulty. Here, easy work went from 50% to 86% of pull requests, hard work improved only 20%, and its rework doubled. (Lesson 6)
  14. Name five outcome metrics and two activity metrics to avoid.
    AnswerLead time, change failure rate, rework, review time and cost per accepted change. Avoid lines of code and pull-request counts. (Lesson 6)
